# Agent workflow

This document explains how work moves between agents. `AGENTS.md` is the
operating contract; this file is the human-readable map.

## Roles are stable, tasks are fresh

- An **agent** is a role: permissions, system prompt, and a narrow job.
- A **session** is a task: one worktree/branch, one task card, one deliverable.
- A subagent always starts with fresh context. Durable context lives in the repo,
  not in a conversation.

The lead never sees full diffs; it sees task cards and structured reports.
Implementers never see each other's conversations. Reviewers see the diff and the
task card, not the implementer's story.

## Roster

| Agent | Mode | Writes | Job |
|---|---|---|---|
| `lead` | primary | task cards, status | decompose, brief, dispatch, close |
| `architect` | subagent | ADRs, contracts, architecture | design gate |
| `probe-dev` | subagent | `kt-probe`, fixtures, goldens | hardware detectors |
| `kconfig-dev` | subagent | `kt-kconfig`, `kt-policy`, `data` | parser, mapping, policy |
| `platform-dev` | subagent | build, verify, report, CLI, xtask | platform work |
| `verifier` | subagent | nothing | acceptance + CI checks |
| `reviewer` | subagent | nothing | independent diff review |
| `researcher` | subagent | nothing | cited upstream facts |
| `docs` | subagent | docs, README, contributing | onboarding |

Human-owned: the root `Cargo.toml`, `rust-toolchain.toml`,
`.github/workflows/**`, `opencode.jsonc`, `.opencode/agents/**`, and licenses.
A crate-level `Cargo.toml` belongs to the crate's owner, but only an approved
dependency set may appear in it. `Cargo.lock` is generated by cargo and reviewed
with dependency changes; nobody hand-edits it.

The human creates or approves the root workspace manifest and the first-time
membership of a new crate. The implementer owns that crate's source and, when
the card allows it, its manifest.

## Lifecycle

1. **Intake — lead.** Create a task card from `docs/tasks/000-template.md`. One
   deliverable, one crate, explicit allowed files, exact acceptance commands.
2. **Design gate — architect.** Check the contract, dependencies, scope, and
   boot-safety impact. Write an ADR if the decision is durable. Small local tasks
   may skip this gate.
3. **Implement — specialist.** Fresh child session on a task branch. Reads the
   task card and only the files it needs. Writes code, tests, and fixtures. Runs
   fast crate checks. Returns the handoff format.
4. **Verify — verifier.** Fresh child session. Runs every acceptance command and
   checks the diff against the allowed scope. PASS/FAIL with exact output.
5. **Review — reviewer.** Fresh child session. Reviews the diff and task card for
   correctness, scope, invented facts, tests, dependencies, and safety.
6. **Close — lead + human.** One fix round in the same child session if needed.
   Human merges. Lead updates the task card and `docs/status.md`.
7. **Capture — architect + lead.** The architect records durable decisions in
   ADRs and updates contracts if the design moved; the lead updates the roadmap
   and `docs/status.md`.

The cap is two fix rounds. Then escalate to the human with both reports.

## Task card

Every task card contains:

- status, owner, branch, dependencies, contract impact;
- goal and why;
- allowed files and forbidden files;
- interface contract;
- exact acceptance commands;
- verified facts and fixture source;
- known risks and open questions.

If a task needs a file outside its allowed list, the implementer stops. It does
not widen scope.

## Handoff

Implementers return exactly:

```
STATUS / TASK / BRANCH / FILES / COMMANDS+results /
CONTRACT IMPACT / DECISIONS / OPEN QUESTIONS / RISKS
```

Long logs go to `target/agent-logs/<task>/`. The lead keeps only the summary.

## Anti-hallucination rules

1. No brief, no work.
2. Read before write.
3. Verify Kconfig symbols in the kernel tree; cite `file:line`.
4. Verify sysfs paths and module names on the machine or in a fixture.
5. Verify crate APIs in local source; no guessed functions or features.
6. Compile/test or it did not happen; exact output required.
7. The reviewer sees the diff, not the implementer's summary.
8. No new dependency without an ADR and human approval.
9. Fixtures are redacted; reviewer checks.
10. Two failed attempts escalate to a human.
11. Local source beats upstream docs; upstream docs beat web search; web claims
    need a URL and date.
12. Keep diffs small; split tasks over ~400 lines or two crates.

## Parallelization

Safe in parallel:

- independent detectors with separate files;
- report renderer and detectors after `kt-core` freezes;
- docs alongside implementation.

Not safe in parallel:

- two tasks editing `kt-core` or a shared schema;
- mapper and parser before the parser interface settles;
- build backend and verifier before artifacts exist;
- two tasks editing the same registry, `Cargo.toml`, or `data/` file.

Rule: one writer per shared file. The lead wires shared registries in an
integration commit. Start serial for the first two weeks; add worktrees only when
tasks are genuinely independent.

## Worktrees

Subagent sessions run in the parent's project directory. For parallel work,
start a separate OpenCode session from the worktree directory, with its own lead.
The config puts new worktrees under `../kernel-tailor-worktrees`.

## What permissions do and do not do

Permission rules match the command text an agent asks to run; they do not
sandbox a binary or its child processes. `cargo test` can still execute code
that writes files. The safety boundary is therefore structural:

- build and install are separate commands;
- install prints the privileged command instead of running it;
- the tool never writes the stock kernel or the default boot entry;
- a human reviews and runs the boot-changing step;
- the verifier and reviewer inspect behavior that a command allowlist cannot
  see.

Treat the rules as a guardrail against accidental commands, not as a sandbox
against a malicious agent.

## Invocation

From the repository root:

```
/task-new <title>
/task-plan <task-file-stem>
/task-do <task-file-stem>
/task-verify <task-file-stem>
/task-review <task-file-stem>
/task-close <task-file-stem>
```

The stem includes the number and slug, for example `003-pci-detector` for
`docs/tasks/003-pci-detector.md`.

Or ask the lead directly: "Use `probe-dev` for TASK-003; the card is
`docs/tasks/003-pci-detector.md`."

## Metrics

Track per task: cycle time, verification failures, review findings, and rework
rounds. If verification fails often, the task cards are underspecified. Fix the
brief before adding more agents.
